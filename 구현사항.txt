개발 착수 전 결정해야 할 주요 설계 결정
1. 데이터베이스
1.1 DB 엔진[결정]: 개발 단계는 SQLite, 배포 시 PostgreSQL 전환(엔진 전환을 염두에 두고 개발할 것)
1.2 핵심 엔티티와 관계 (현재 모델 -> 확장)[결정]
- User(커스텀 User), Team, TeamMembership(역할: 팀장/팀원), Project, Meeting, Recording, Transcript, Minutes(통일 회의록), Summary, Question, Answer, Comprehension(이해도 검증), QuizQuestion(선택지, 정답), QuizAttempt
- 팀-유저는 현재 ManyToMany 직결 -> 중간 모델(TeamMembership)로 변경
- Team과 Meeting 사이에 Project 계층이 필요 (Team 1:N Project 1:N Meeting)
1.3 익명 질문의 익명성 범위[결정]: 서버에는 저장하되 화면에서만 숨김
1.4 삭제/보존 정책[결정]
- 팀/회의 삭제 시 CASCADE 실행, 소프트 삭제(is_deleted) 도입 안 함
- DB 행 삭제 시 MEDIA_ROOT의 녹음 파일도 함께 삭제(post_delete 시그널)
- 녹음 원본과 회의록의 보관 기간: 영구 보관
1.5 마이그레이션[결정]:커스텀 User로 개발 착수

2. 인증/권한
2.1 User 모델[결정]: 비어 있는 'class User(AbstractUser): pass'로 시작
2.2 로그인 방식[결정]: 자체 로그인(아이디/비밀번호)만 구현
2.3 접근 제어[결정]: 팀 소속자만 해당 팀의 회의/대화방/회의록 열람 (login_required + 팀 멤버십 검사)
2.4 팀 참여 방식[결정]: 초대 코드(무작위 문자열)
2.5 역할 구분[결정]: 회의 생성/종료 권한은 팀장 전용 권한
2.6 팀장 지정[결정]: 팀 생성자 = 팀장(TeamMembership 역할=팀장), 초대 코드는 팀장이 재발급 가능(재발급 시 이전 코드 무효)
- 팀장 양도/탈퇴는 이번 범위에서 제외

3. 회의 녹음 처리
3.1 녹음 입력 방식[결정]: 브라우저 녹음(MediaRecorder, webm) 후 제출 시 서버로 업로드. 녹음 파일 직접 선택 업로드(mp3/webm)도 허용
3.2 녹음 주체[결정]: 회의당 단일 녹음
3.3 파일 저장소[결정]:
- 로컬 MEDIA_ROOT 저장(배포 시까지도 최대한 MEDIA_ROOT로 버티기)
- 길이:30분 내외(업로드 후 서버에서 길이 검증), 파일 크기 상한도 함께 설정(길이 검증 전 1차 방어), 허용 포맷:webm, mp3
3.4 음성 인식(STT)[결정]: 개발 단계는 로컬 모델, 배포 시 외부 api로 전환. 언어:한국어, 화자 분리:나중에 구현(우선순위 낮음, 일단은 안 함)
- stt 모델 교체 대비를 위해 wrapper 인터페이스 추가
3.5 회의 상태 머신[결정]:  상태 머신 도입(생성 -> 제출 -> 처리중 -> 완료/실패), Meeting.status 필드(기존 ended 대체)
- 3.3.2의 '종료 버튼' = 녹음 중지, '제출 버튼' = 상태를 제출로 전환하고 처리 시작
- 실패 상태에서는 재시도(재제출) 가능

4. AI(LLM) 연동
4.1 [삭제]
4.2 용도별 호출 구분[결정]:
- (a) 통일 회의록 생성: 2단계
-- (a-1) STT: 개발 중에는 로컬 stt, 배포 시 stt api(제출된 녹음 -> 텍스트 추출, Transcript 저장)
-- (a-2) 회의록 정리: 클로드 api(Transcript -> 단순 텍스트 회의록, Minutes 저장)
- 회의록(전문 정리)과 요약(b, 압축)은 구분한다. 요약은 회의록을 입력으로 사용
- (b) 회의 요약(3.4): 클로드 api
- (c) 대화창 LLM 답변(3.3.4.1): 클로드 api
- (d) 이해도 검증 문항 생성: 클로드 api(객관식 문제만 생성->채점은 기계적으로 처리)
- (e) 답변 초안 생성: 클로드 api
4.3 비동기 처리[결정]: 백그라운드 스레드로 처리
- 스레드 종료 시 DB 연결을 닫을 것(connection.close())
- 서버 재시작 등으로 '처리중'에 멈춘 회의는 일정 시간 초과 시 '실패'로 전환(타임아웃 복구)
4.4 진행률 표시 방식[결정]: 폴링(주기적 AJAX), 회의 status 조회 엔드포인트 사용
4.5 맥락 유지 범위[결정]:
- 대화 시 프롬프트에 넣는 맥락(해당 프로젝트 회의 요약의 누적)과 토큰 한도 초과 시 처리 방식: 한도 초과 시 가장 오래된 회의 요약부터 컨텍스트에서만 제외(DB에서 삭제하지 않음). 시스템 프롬프트와 현재 질문은 항상 포함
-- 토큰 계산: 글자 수 근사[클로드 api 사양을 알아보고 그에 근접하게 설정]
-- 회의록 추가 후 제외 한도에 근접 시, 새 회의를 열려 하면 기존 회의록이 제외될 수 있다는 경고 표시
4.6 실패 처리[결정]: 실패를 알리는 단일 메세지
4.7 개인정보/보안[결정]: 회의 내용(음성 포함)이 외부 LLM/STT API로 전송됨을 약관에 명시, 회원가입 시 동의 체크
4.8 API 키 관리[결정]: 환경변수로 관리, 저장소에 커밋하지 않음(.env는 .gitignore)
4.9 클로드 모델 선택[결정]: 용도별로 설정값(settings)으로 분리하여 교체 가능하게 함(회의록 정리/요약/대화/문항 생성/답변 초안)

5. 대화창
5.1 대화 모델[결정]: Conversation(회의별 대화방, 종류=LLM/익명질문, 소유자), Message(보낸 쪽: 사용자/LLM/익명질문자, 내용, 시각). LLM 호출은 4.9의 클로드 모델 사용
5.2 익명 질문 <-> LLM 대화 토글[결정]: 별도 대화방 2개('토글'이라는 것은 ui/ux상의 의미, 실제 구현은 2개의 별개의 페이지로 구현)
5.3 LLM 대화 기록의 공개 범위[결정]: 개인 전용, 팀에 공유하지 않음(Conversation에 소유자 필드 추가)
5.4 실시간성[결정]: 익명 질문 수신 화면은 폴링. LLM 대화 답변은 요청-응답(동기)으로 처리

6. 이해도 검증 (3.6) 및 질문 답변 (3.5)
6.1 이해도 검증 형식[결정]:
- llm이 회의록을 기반으로 객관식 문제 3개를 생성->팀원들이 답변->자동 채점
- 문항은 회의 완료 시 1회 생성하여 저장(정답은 서버에만 두고 채점도 서버에서 수행). 응답 형식은 JSON으로 받고 파싱 실패 시 재시도
- 기준 회의록은 최신 버전. 회의록 재생성 시 문항도 새로 생성하고 이전 시도는 보존
6.2 결과 저장 단위[결정]: 개인별 점수/오답 결과를 저장함, 팀장은 팀원 결과를 볼 수 없음
6.3 질문 답변(3.5) 주체[결정]: LLM이 답변 초안 생성 후 팀장이 수정, 답변은 비공개(질문자 본인에게만 표시)
- 이를 위해 Question에 작성자(FK) 저장(화면에서는 팀장에게도 숨김), 질문자가 자신의 질문/답변을 보는 화면 필요(1.3과 연계)

7. 산출물(회의록)

7.3 회의록 구조[결정]: 단순 텍스트
